### Анализ системы и C4-диаграмма трейсинга

| Система | Точки потенциальных проблем | Данные для трейсинга |
|-|-|-|
| Online Shop API | - Создание заказа<br>- Загрузка 3D-модели<br>- Передача заказа в CRM | - ID заказа<br>- Timestamp операций<br>- Статус загрузки файла<br>- Параметры 3D-модели |
| CRM API | - Проверка и подтверждение заказа<br>- Передача в MES<br>- Статусные переходы | - ID заказа<br>- Статус подтверждения<br>- Время обработки<br>- Пользователь, который обработал |
| Message Queue (RabbitMQ) | - Доставка сообщений между сервисами<br>- Потеря сообщений<br>- Задержки в очереди | - ID сообщения<br>- Источник сообщения<br>- Получатель<br>- Время нахождения в очереди |
| MES API | - Расчет стоимости<br>- Старт производства<br>- Завершение производства | - ID заказа<br>- Время расчета<br>- Статус производства<br>- Оператор, ответственный за заказ |
| 3D File Storage | - Сохранение файлов<br>- Доступность файлов | - ID файла<br>- Размер файла<br>- Время загрузки<br>- Статус хранения |

### Мотивация внедрения трейсинга

| Метрика | Технический эффект | Бизнес-эффект |
|-|-|-|
| Время обработки заказа | Точное определение задержек на каждом этапе | Сокращение среднего времени выполнения заказа |
| Отказоустойчивость | Быстрое обнаружение сбоев в коммуникации между сервисами | Повышение надежности системы и удовлетворенности клиентов |
| Мониторинг производительности | Идентификация узких мест в архитектуре | Оптимизация инфраструктуры и снижение издержек |
| Аудит операций | Полная прослеживаемость изменений статусов заказа | Повышение прозрачности бизнес-процессов |
| Качество обслуживания | Быстрое реагирование на проблемы в системе | Улучшение репутации компании и удержание клиентов |

# Предлагаемое решение

[Диаграмма](./alex_c4_model.drawio)

### Компромиссы:

1. Ограничения трейсинга:
- Для MES потребуется дополнительная интеграция, так как это проприетарная система с возможными сложностями внедрения трейсинга
- Высокая нагрузка на системные ресурсы при полном трейсинге всех операций
- Значительные затраты на модификацию существующей архитектуры
- Возможное снижение производительности систем при тотальном логировании

2. Экономическая целесообразность:
- Стоимость внедрения систем распределенного трейсинга может превышить краткосрочный эффект
- Потребуется дополнительное оборудование для хранения и обработки трейс-данных
- Необходимость переобучения команды разработки

Безопасность системы трейсинга:

Внутренний контур:
- Многофакторная аутентификация для доступа к системе трейсинга
- Ролевая модель доступа:
  * "Администратор" - полный доступ
  * "Поддержка" - просмотр трейсов без возможности изменения
  * "Разработчик" - анализ технических деталей
- Шифрование персональных данных в трейс-логах
- Автоматическое удаление логов по истечении 90 дней
- Журналирование всех действий пользователей в системе трейсинга

Внешний контур:
- Изолированная сеть для системы трейсинга 
- Белый список IP-адресов
- Использование VPN для удаленного доступа
- Сертификаты с ограниченным сроком действия
- Мониторинг подозрительной активности

### Дополнительное задание:

Автоматический мониторинг и алертинг:

Метрики процесса заказа:
1. Время между статусами
2. Количество застревающих заказов
3. Средняя длительность производства
4. Процент просроченных заказов

Алертинг:
- Уведомления при превышении порога времени между статусами
- Alerts в Slack/Telegram-боты для менеджеров
- Автоматическая эскалация при длительном простое заказа

Техническая реализация:
- Использовать Prometheus для сбора метрик
- Grafana для визуализации 
- AlertManager для управления алертами
