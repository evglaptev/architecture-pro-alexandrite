### Мотивация

В текущей архитектуре системы MES существует несколько проблем производительности:
- Медленная загрузка страницы со списком заказов (2-3 минуты, в сложных случаях до 30 минут)
- Высокая нагрузка на систему при расчете стоимости изделий
- Рост количества заказов (линейный рост +100 заказов ежемесячно)

Кеширование позволит решить следующие проблемы:
- Ускорить доступ к часто запрашиваемым данным
- Снизить нагрузку на базу данных
- Улучшить отзывчивость пользовательского интерфейса

Элементы системы для кеширования

| Компонент | Тип данных | Цель кеширования |
|-|-|-|
| MES API | Результаты расчета стоимости изделий | Ускорение повторных расчетов |
| MES DB | Списки заказов по статусам | Быстрый доступ к актуальным заказам |
| 3D File Storage | Метаданные 3D-моделей | Снижение нагрузки на файловое хранилище |

### Предлагаемое решение

Тип кеширования: Серверное кеширование

Выбор серверного кеширования обоснован следующими причинами:
- Централизованное управление кешем
- Единый источник кешированных данных для всех клиентов
- Возможность тонкой настройки политик кеширования

Паттерн кеширования: Cache-Aside

Причины выбора:
- Простота реализации
- Гибкость в управлении кешем
- Возможность постепенной миграции

Сравнение паттернов:

| Паттерн | Преимущества | Недостатки |
|-|-|-|
| Cache-Aside | - Простота реализации<br>- Гибкость<br>- Низкая связанность | - Возможные промежуточные состояния<br>- Дополнительная логика в коде |
| Write-Through | - Консистентность данных<br>- Автоматическое обновление | - Overhead при записи<br>- Сложная реализация |
| Refresh-Ahead | - Проактивное обновление<br>- Меньше задержек | - Сложное прогнозирование<br>- Высокие накладные расходы |

```mermaid
sequenceDiagram
    participant Оператор
    participant MES Frontend
    participant MES Backend
    participant Redis
    participant MES DB
    participant Message Queue
    
    Оператор->>MES Frontend: Открытие страницы заказов
    MES Frontend->>MES Backend: GET /orders?status=MANUFACTURING_STARTED&page=1
    
    MES Backend->>Redis: GET orders:MANUFACTURING_STARTED:page:1
    
    alt Кеш-попадание
        Redis-->>MES Backend: Закешированные данные заказов
        MES Backend-->>MES Frontend: Список заказов (быстро)
    else Кеш-промах
        Redis-->>MES Backend: null
        MES Backend->>MES DB: SELECT * FROM orders WHERE status='MANUFACTURING_STARTED' LIMIT 20
        MES DB-->>MES Backend: Данные заказов
        MES Backend->>Redis: SET orders:MANUFACTURING_STARTED:page:1 [данные] EX 300
        MES Backend-->>MES Frontend: Список заказов
    end
    
    Note over MES Backend,Message Queue: Обработка изменения статуса заказа
    
    MES Backend->>Message Queue: Publish order_status_changed event
    Message Queue-->>MES Backend: Подтверждение публикации
    
    MES Backend->>Redis: INVALIDATE orders:*:page:*
    MES Backend->>MES DB: UPDATE orders SET status = ? WHERE id = ?
    
    Note over MES Backend: Асинхронное обновление кеша
    MES Backend->>Redis: Перекеширование актуальных данных
```


### Стратегия инвалидации кеша

| Стратегия | Преимущества | Недостатки |
|--|--|--|
| Временная | - Простота реализации<br>- Автоматическое обновление | - Возможное отображение устаревших данных |
| По ключу | - Точечное обновление<br>- Гибкость | - Сложность реализации<br>- Необходимость явного управления |
| Программная | - Полный контроль<br>- Гибкость | - Высокая сложность реализации |

Выбрана комбинированная стратегия:
- Временная инвалидация (TTL)
- Программная инвалидация по ключевым событиям

Причины выбора:
- Автоматическое устаревание данных
- Возможность принудительного обновления
- Гибкость настройки для разных типов данных

Параметры инвалидации:
- Расчеты стоимости: TTL 24 часа
- Списки заказов: TTL 1 час
- Принудительная инвалидация при изменении статуса заказа

Технические детали реализации

1. Использовать распределенный кеш Redis
2. Внедрить абстракцию кеширования в MES API
3. Добавить механизмы логирования и мониторинга кеша
4. Реализовать постепенную миграцию с fallback на прямое обращение к БД

Риски и ограничения

- Возможное увеличение сложности кода
- Необходимость дополнительного обучения команды
- Начальные трудозатраты на внедрение
